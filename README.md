# ArmyClashTest
README - Army Clash Test
1. Введение
Проект реализует базовую симуляцию сражений двух армий в стиле Army Clash. Каждая армия состоит из случайно сгенерированных юнитов, которые сражаются до полного уничтожения противника. 

2. Архитектура проекта
Архитектура построена как гибрид State Machine + MVP/MVC - State Machine обеспечивает ясный игровой цикл, а MVP упрощает тестирование и разделение логики:
•	GameStateMachine - управляет глобальными состояниями игры (подготовка, бой, завершение, смена сцен).
•	GameFlowController - посредник для управления объектами на сцене - инициализация фабрики, контроллера юнитов и т.д.
•	UnitsFactory - отвечает за создание юнитов.
•	UnitsController - менеджер юнитов, управляет жизненным циклом юнитов и команд: распределение юнитов по командам, выбор и порядок действий юнитов. 
•	Unit - фасад, объединяющий контроллеры здоровья, атаки, движения и визуала юнита.
•	GameInfoService - хранит рантайм-статистику боя (количество юнитов, победитель).
•	GameDataService - хранит статистику игры (количество боёв, количество побед каждой команды).
•	ConfigsProvider - предоставляет доступ к хранилищу конфигов игры (характеристики юнитов, формы, размеры, цвета).
•	GameUIController, MainMenuUIController - посредники для управления панелями интерфейса.

3. Юниты
Юнит реализован как композиция нескольких контроллеров:
•	HealthController - управляет HP, смертью, событием изменения здоровья.
•	AttackController - учитывает задержку атаки, наносит урон, вызывает событие OnAttack (можно использовать для визуализации).
•	MoveController - отвечает за движение к цели и ориентацию. Реализовано 2 варианта движения MoveController - движение через Vector3.MoveTowards, MoveControllerAI - движение через NavMesh.
•	UnitInfo - хранит характеристики (ATK, HP, SPEED, ATKSPD) после применения всех модификаторов, имя юнита, размер и текущую цель.
•	UnitVisual - управляет отображением модели (форма, цвет, размер, вывод текущего количества здоровья). 
Для оптимизации юниты берутся из пула, а вместо создания моделей (из конфига) идёт смена меша и применение нового материала (характеристика цвета). Это снижает нагрузку на GC и ускоряет создание армий. В дальнейшем, в зависимости от задач (нестандартные модели, анимации и т.д.) можно будет легко переделать создание модели - изменив только UnitVisual.

Юнит реализует интерфейс IUnit, предоставляя методы:
•	SetTarget(IUnit target)
•	CanAttack() - проверка дистанции и перезарядки удара. Для проверки дистанции используется размер юнита и размер цели
•	Attack() - нанесение урона.
•	MoveTowards(float deltaTime) - движение к цели.
•	Hit(int damage) - получение урона.
•	StopMoving() - остановка движения.

4. Логика боя
За ведение боя отвечает UnitsController. Он делает запрос на создание 2 команд по х юнитов (в зависимости от конфига). А потом обновляет действие каждого юнита по очереди. Обновление идёт по командам. Алгоритм обновления юнита:
1.	Проверка состояния (жив/мертв).
2.	Проверка наличия цели.
3.	Поиск ближайшего врага.
4.	Проверка дистанции до цели.
5.	Движение к цели.
6.	Проверка возможности атаки.
7.	Ожидание атаки.
8.	Атака (нанесение урона).
Удаление мёртвых юнитов происходит во втором проходе, чтобы не ломать итерацию.
После того как все команды обновятся информация о текущем состоянии команд передаётся в GameInfoService.

5. UI и статистика
•	GameUIController управляет панелями и их взаимодействием в игровой сцене (панель старта битвы, панель победы, панель статистики команд).
•	MainMenuUIController управляет панелями и их взаимодействием в сцене меню (одна панель с выводом статистики о пройденных боях).
•	GameInfoService содержит:
-	количество юнитов в каждой команде,
-	OnOneTeamAlive(когда осталась одна команда) и OnUnitsCountUpdate(когда обновились данные команды)
UI берёт данные из GameInfoService и отображает их на экране.
GameFlowController - подписывается на OnOneTeamAlive и вызывает завершение боя.

6. Конфиги
Для работы конфигами добавлен специальный редактор (оформлен через OdinInspector). 
Открыть редактор можно через Tools - Config Editor - Open Editor.
Все конфиги наследуются от ScriptableObject:
•	GlobalConfig - содержит количество юнитов в каждой команде. Можно добавить глобальные настройки, по типу: конфига звука, включение/выключение дебага и т.д.
•	UnitConfigsProvider - содержит конфиги для генерации юнитов:
-	baseConfig - конфиг базовых характеристик
-	shapes - список возможных модификаций форм
-	sizes	- список возможных модификаций размеров
-	colors	- список возможных модификаций цветов
•	Все конфиги находятся в папках по пути Assets/Resources/Configs (можно изменить через настройки редактора).
•	В папке /Global находятся конфиги которые можно получить ConfigsProvider
•	В папке /Unit находятся подпапки с конфигами размеров, формы, цветов.
•	Конфиг базовых характеристик содержит фиксированный набор из 4 базовых характеристик по ТЗ
•	Все остальные конфиги-модификаторы содержат динамический список характеристик, что позволяет создавать различные модификации без изменения кода. (Важно: если в списке добавить 2 одинаковые характеристики, например, в кнофиге размера 2 раза указать HP, то они будут суммированы при использовании в коде)

8. Проблемы и ошибки и т.д.
•	При настройках, заданных в ТЗ возможны ситуации, когда юнит создаётся с 0-м значения здоровья. В таких случаях в консоль будет выведен лог типа "Dead on start Unit Sphere Small Green", отображающий при каких характеристиках это произошло.
•	Для реализации ближнего боя используется размер юнита. Было принято решение добавить в конфиг размера переменную _modelSize, которая одновременно влияет на размер модельки и используется для расчёта возможности атаки. 
Формула определения дистанции атаки: (unit.Size + target.Size) * 0.55 - коэффициент выбран эмпирически для визуального комфорта. При использовании MoveControllerAI юнитам устанавливается радиус равный половина от размера и как раз 0.05 делает чтобы юниты не подходили впритык.
В дальнейшем можно будет переделать систему, например, на коллайдеры и добавить отдельную переменную отвечающую за размер коллайдера.
•	Установка меша вместо замены модельки и установка цвета, вместо материала/текстуры это временны производительный вариант в рамках ТЗ. Я не исключаю возможность анимирования полноценного юнита через шейдеры (запечённые анимации), но в дальнейшем, при появлении нормальных моделей придётся значительно переделывать визуализацию юнита. Скорее всего придётся составлять фабрику по генерации модели.

9. Дополнительная функцию, которая может выделить игру среди других
Игру можно развивать в разных направлениях, но отталкиваясь от того что сейчас армии генерируются случайно, и игрок не может на это повлиять пришла идея дать возможность игроку участвовать в сражении.
Было бы интересно дать игроку систему умений, с помощью которых он может влиять на ход битвы:
- бафы для своей армии
- дебафы для врагов
- различные точечные заклинания во врагов по типу удара молнией
- заклинания по области в виде метеорита, болота, потока лавы и т.д. которые могут влиять на обе команды.
Добавь такую механику мы превращаем игрока не просто в полководца армии, а в "бога", который способен влиять на ход битвы.
Функция не была реализована т.к. она слишком объёмная. Предполагается, что должен быть:
- инвентарь для выбора "заклинаний" (SpellsDeck, SpellsSlots и т.д.)
- система взаимодействия игрока с юнитами (например, клик через коллайдер) – UnitSelectionSystem c блокировки выбора юнитов.
- система использования заклинаний - SpellsController. Логика самих заклинаний -  ISpell, Spell и различные реализации заклинаний. Конфиги самой системы (сколько может быть заклинаний у игрока, как часто он может их использовать) – SpellsConfigProvider, SpellConfig, SpillVisualConfig и т.д.
Если в дальнейшем развивать эту функцию, то можно включить её в мета-геймплей:
- получение уровня для открытия новых заклинаний
- получение ресурсов для улучшения и использования заклинаний
- формирование "колод"/наборов с часто используемыми заклинаниями.
